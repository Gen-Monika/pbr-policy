# 预期结果（expected）

本目录给出**校验用的预期值**，供读者确认自己的复现是否成功。

## 校验策略：确定性计数为主，墙钟比值为参考

绝对墙钟强依赖机器、负载与缓存状态，跨机器不可比——本项目自己的跨批数据就证明了这点：同配置同代码的 $K=1$ 墙钟在不同批次间相差 1.35–1.58 倍。因此：

- **主要校验**用 `openfoam.csv` 的 `nbuild_exact` 列：重建次数与累计迭代数是确定性的，只要代码与算例一致，**必然**逐位对上。
- **参考**用 `total_median` 与 `total_min`/`total_max`：这些是压力模块耗时的绝对值（秒），只能用来判断"量级对不对"，不能用来判断"复现成功与否"。

## 文件

| 文件 | 内容 |
|---|---|
| `openfoam_iters.csv` | **首选校验量**：六 damBreak 配置 + sth，各模式的累计迭代数与步数 |
| `openfoam.csv` | 重建次数与压力模块耗时（耗时为参考量） |
| `aspect.csv` | Blankenbach case 2a 的 online 模式：步数、重建次数、累计迭代 |
| `moose.csv` | step6a 的 K1 与 online 模式：重建次数、累计迭代 |
| `elmer.csv` | FSSA_perlin2d（`stabilized.sif`）的 online / 固定 K=1 / 官方默认 / 永不重建 |
| `lamem.csv` | 三组等价性验证的输出文件数与差异计数 |

**为什么迭代数比耗时更可靠**：累计迭代数完全由决策序列与矩阵性质决定，与机器性能无关。`K1`/`K3`/`DIC` 在全部配置、全部轮次上逐位相同；`ONLp` 因依赖实时计时估计 $\rho$，个别决策会变，迭代数因此有 0.2%–1% 的浮动（见下表）。

## `openfoam.csv` 的列

| 列 | 含义 |
|---|---|
| `config` | 配置名，对应 `../cases/openfoam/<config>/` |
| `mode` | `K1`（每步重建）/ `K3`（固定周期 3）/ `ONLp`（在线策略，RCOST=step） |
| `nbuild_exact` | 重建次数。**非空即表示该模式跨全部轮次逐位相同，可直接作为校验量** |
| `nbuild_observed` | 实际观测到的全部取值（多个用 `|` 分隔） |
| `nbuild_variable` | `yes` 表示在线策略的重建次数在轮次间有变化（见下） |
| `total_median` | 压力模块耗时的中位数（秒），按论文公式计算 |
| `total_min` / `total_max` | 跨全部轮次的最小/最大值 |
| `rounds` | 合并的轮次数（来自三个批次：七配置批 3 轮、全模式批 3 轮、串行补测 8 轮）。`sth` 的两行改用 $B_0=100$ 批（`sthB100k` / `sthB100a`，各 3 轮），见下方说明 |

**`sth` 的两行（`K1` 与 `ONLp`）已换成 $B_0 = 100$ 批次的实测**（2026-10-31），与脚本口径一致。旧 $B_0 = 50$ 批次的值记在这里备查：`K1` 耗时 12.55 / 11.874 / 14.348 s，`ONLp` 重建次数 1320 / 1352 / 1360、耗时 5.864 / 5.626 / 6.502 s。两批的 `K1` 重建次数完全相同（23464，每步都重建，与 $B_0$ 无关），差别只在耗时；`ONLp` 则两者都变（重建次数 1320→1696，因为预热多 50 步就多一批强制重建）。

## 各模式的确定性程度（实测，跨全部轮次）

| 配置 | 轮数（K1/ONLp） | K1 / K3 / DIC 迭代数 | ONLp 迭代数观测值 |
|---|---|---|---|
| fx | 14 / 14 | 7957 / 12527 / 68115（逐位一致） | 13368、13663 |
| l15 | 14 / 14 | 5765 / 10335 / 68115（逐位一致） | 10444、10544 |
| l20 | 14 / 14 | 4688 / 9361 / 68115（逐位一致） | **9474（逐位一致）** |
| fine | 6 / 6 | 16865 / 31276 / 299248（逐位一致） | 35498、35685、35752、35953、35958 |
| fl30 | 6 / 6 | 11953 / 26373 / 299248（逐位一致） | 37543、37555、37696 |
| x3 | 6 / 6 | 43819 / 72252 / 788464（逐位一致） | 81323、81475、81713、81810、82119、82159 |
| sth | 3 / 3 | 76258（仅 K1） | 126804、126863、124807 |

**`sth` 的复现口径与六个 damBreak 有两处必须一致**（`scripts/run_openfoam.sh` 已内置）：`endTime = 20`（不是官方 50、也不是历史长批的 100）、共同窗口为前 $5866$ 个物理步。预热基数 $B_0$ 自 2026-10-30 起与六个 damBreak 相同，取 **100**；注意统一的是参数值而非覆盖量——$B_0$ 在 OpenFOAM 里按时间步计，sth 每步约 4 次压力求解、damBreak 约 3 次，故 sth 实际预热约 400 次求解。旧版本的 $B_0 = 50$ 无记录依据，用它会得到不同的决策序列，那不属于「环境差异」；排查时不要改回 50 去「对齐」旧值。

（`K3` 轮数为 `K1` 减去 3：七配置批只跑 `K1`/`ONLp`，未跑 `K3`/`DIC`。）

**校验建议**：先比 `K1`/`K3`/`DIC` 三列的迭代数——它们必须精确对上，对不上就是环境或配置问题。

`ONLp` 只看是否**落在合理范围内**：实测中 `fx` 出现过 13368、13663 与 13919 三种取值（重建步 173 / 173 / 170），即在线策略的决策会随计时噪声改变，迭代数与重建次数随之浮动 2%–4%。这与论文 §8 记录的"在线策略依赖实时 $\hat\rho$，微小波动即可改变个别决策"一致——**`ONLp` 的任何单一取值都不构成校验失败**。

若 `ONLp` 的重建次数与上表相差超过 10%，或完全不重建、或每步都重建，才需要排查（通常是 `PBR_PETSC_BENCH` 没开）。

注：`x3` 的 `K1` 步数是 1229 而其余模式 1231，这是自适应时间步导致的（$K=1$ 与其余策略的轨迹略有差异），不是 bug。

## 为什么在线策略的重建次数会变

`K1` 与 `K3` 是纯确定性策略，全部 14 轮（或 6 轮）逐位相同。`ONLp` 依赖**实时的分解耗时测量**来估计成本比 $\rho$，测量有噪声，因此个别重建决策会变：

- `fx`：518 或 524 次（差 1.1%）
- `fine`：878 或 881 次
- `x3`：1346 / 1349 / 1352 次
- `sth`：1696、1696、1848 次（$B_0 = 100$ 批；旧 $B_0 = 50$ 批为 1320、1352、1360 次）

（`sth` 每步 4 次压力求解，重建按求解次数计——424 个重建步 × 4 = 1696；六个 damBreak 每步约 3 次，故 `fx` 的 173 个重建步对应 518 次。这一列的数一律是**重建次数**，不是重建步数。）

`l15`、`l20`、`fl30` 的 `ONLp` 重建次数在全部轮次中**逐位相同**（分别为 539、539、761）。

**这不影响结论**：重建次数的 0.2%–3% 波动不足以解释压力节省百分比的 10–20 pp 波动（后者的成因是单次分解耗时本身的测量噪声，见论文 §8）。

读者复现时，`ONLp` 的重建次数落在上表列举的取值附近即属正常。

## 压力模块耗时的公式

```
ΣtConvert + ΣtPCSetup + tApplyAccum(最终值) + ma中位 × nApplyCalls(最终值)
```

对 `field=p_rgh` 的**全部行**求和（含 `rep=8` 的每步一行；漏掉这些行会低估约三分之一）。

## 已知的跨批差异

小配置（`fx`/`l15`/`l20`，2268 单元）的压力模块耗时在批次间的极差可达 30%–40%，因为单次矩阵分解仅 10–16 ms，与宿主负载波动同量级。大配置（`fine`/`fl30`/`x3`）极差在 5% 以内。

**因此 `total_median` 对三个小配置只有量级参考价值，对三个大配置可作为较强的对照。**

## 复现失败时的排查顺序

1. 重建次数对不上 → 检查环境变量（`PBR_PETSC_FREEZE_AT` 是否设了？`PBR_PETSC_ONLINE_RCOST=step`？）
2. 重建次数对上了但迭代数不对 → 检查 `fvSolution` 的容差是否被改回官方值（$10^{-7}$/$0.05$）
3. 都对了但耗时差很多 → 正常，比机器的绝对性能
4. `ONLp` 完全不重建或每步都重建 → `PBR_PETSC_BENCH` 没设成 1，在线策略拿不到 $\rho$ 样本

## ASPECT 的校验量（`aspect.csv`）

三个量按确定性递减排列：

1. **步数 $1626$**：完全由 `End time = 0.1` 与自适应时间步决定，逐位必对。若得到 $6638$ 步，说明 `case.prm` 末尾的 `set End time = 0.1` 被删掉了。
2. **累计迭代数 $25402$ 或 $25454$**：与 OpenFOAM 同理，但 online 模式依赖实时 $\hat{\rho}$，三轮观测到两个取值。落在两者之一即正常。
3. **重建次数 $108$/$110$**：随迭代数同步变化，$108$ 对应 $25402$，$110$ 对应 $25454$。

端到端验证时（2026-10-30）在干净目录重跑得到 `steps=1626 rebuilds=110 total_its=25454 wall=227s`，与上表 $25454$/$110$ 逐位相同。墙钟 $227$ s 快于记录的 $297$–$319$ s，属机器与负载差异，不作校验用。

## Elmer 的校验量（`elmer.csv`）

Elmer 这套必须用 `stabilized.sif`（官方目录里另有一个 MINI 单元的 `Stokes_prognostic_nonlWeert.sif`，不是本文用的那个）。`scripts/run_elmer.sh` 已固定文件名，并自动注入判据开关。

确定性校验量：**求解次数 $271$、重建次数 $270$**。在线策略在这个算例上稳定退化为几乎每次重建（这正是论文要说明的行为），因此这两个数与固定 $K=1$ 的接入版**逐位相同**，累计迭代数同为 $5613$。

不接入判据（`PBR_POLICY` 不设或注入缺失）时得到官方默认的 $272$ 次求解 / $5626$ 次迭代；这个差异只反映判据开关本身带来的第一次求解记账差异，不代表算例改动。
